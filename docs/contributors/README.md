# Student contribution portfolios

The [contributor directory](../../CONTRIBUTORS.md) links to one Markdown portfolio
per student in the NYU Fall 2026 VIP. Research, code, writing, reviewing, and
presentations all count. Your portfolio makes that work easy to find through
links to issues, pull requests, reviews, and artifacts.

## First contribution

Use [the student guide](../student-start.md) for GitHub, fork, clone, and pull
request instructions. Your first PR can just introduce you:

1. Copy [`_template.md`](_template.md) to
   `docs/contributors/YOUR-GITHUB-USERNAME.md` in your contribution branch,
   replacing `YOUR-GITHUB-USERNAME` with your actual username.
2. Add your preferred public display name (your username is sufficient),
   GitHub profile link, and optional area of interest. Leave the contribution
   table empty until you have work to record, and remove instructional comments.
3. Add an alphabetical row to [CONTRIBUTORS.md](../../CONTRIBUTORS.md) linking
   your GitHub profile and your portfolio file. Remove the empty-roster notice
   if yours is the first entry.
4. Open a pull request with those two files and a short introduction. A separate
   issue or completed research deliverable is not required for enrollment.

Use only your preferred public name and GitHub profile. Keep private emails,
student IDs, grades, and personal academic records outside the repository.

## Add your work as you go

Add one short table row per meaningful contribution, normally in the same PR
as the work. Include a date, what you did and your role, a link to the evidence,
and collaborators when applicable. Plain role names such as literature review,
coding, analysis, or reviewing are enough to get started.

Link the original issue, PR, review comment, document, result, or presentation.
The linked issue or PR shows whether the work is open, merged, or closed; there
is no separate portfolio status to maintain and no follow-up PR needed just to
mark work complete. If the PR URL is not available yet, use an issue or artifact
link. You can add the PR link on the same branch once the PR exists.

Describe what you actually contributed. If an entry describes future work,
start its description with **Planned:** and link the issue; do not describe a
planned run or result as completed. Negative findings and useful failed
approaches also belong in the record when supported by evidence.

Study-selection work counts when it leaves reviewable evidence: a sourced
question exploration, substantive critique, bounded reproduction attempt, or
reasoned recommendation to reject a proposal. If the cohort does not select a
proposal, link the existing review or decision; do not invent follow-up work or
add rows merely to increase activity counts.

For shared work, link your [Individual task](../issue-workflow.md) and say who did
what. Multiple students can link the same PR or artifact from their separate tasks
while describing their own contributions. Independent attempts at the same assignment
have separate tasks and their own evidence. For reviewing or presenting,
link the substantive review comment or saved slides and supporting research.
One entry per useful outcome is enough; no per-commit log is needed.

## Optional: CRediT roles

For research reports, the [CRediT roles](https://credit.niso.org/contributor-roles-defined/)
give consistent names to contribution types. You can use them in your portfolio
when helpful. These examples are guidance; select only roles you performed.

| Contribution in this VIP | Possible CRediT roles | Useful evidence |
| --- | --- | --- |
| Literature search and synthesis | Investigation; Writing – original draft | Source-linked notes and a reviewed synthesis |
| Reproducing the pilot or a published result | Validation; Investigation | Commands, provenance, comparison, and limitations |
| Exploring, critiquing, selecting, or rejecting a proposed question | Conceptualization; Methodology; Investigation, as applicable | Sources, feasibility or reproduction evidence, review, and decision rationale |
| Hypotheses and experiment design for the selected study | Conceptualization; Methodology | Reviewed design and decision record |
| Harness, agents, tooling, or tests | Software; Validation where applicable | Implementation PR and relevant checks |
| Scenario data and trace documentation | Data curation | Versioned data, schema, and provenance |
| Statistical analysis and interpretation | Formal analysis | Analysis code, denominators, and findings |
| Figures and presentation materials | Visualization; Writing – original draft | Versioned figures or slides linked to supporting evidence |
| Documentation and research writing | Writing – original draft; Writing – review & editing | Reviewed document or substantive revision |
| Reviewing code, methods, or writing | Software; Validation; Writing – review & editing, as applicable | Review comments and the specific improvement or check |
| Coordinating deliverables and handoff | Project administration | Reviewed plans, decision records, and handoff artifacts |

Other CRediT roles may apply when supported by the work. CRediT records contribution
types; it does not determine authorship. See the
[cohort guide's credit and authorship discussion](../cohort-guide.md#credit-and-authorship).

## Visibility and corrections

Keep your profile and directory link on `main` through reviewed PRs. Follow
[CONTRIBUTING.md](../../CONTRIBUTING.md) for Git authorship and GitHub attribution.
GitHub activity graphs show only some forms of work; portfolios also surface
literature, design, reviewing, analysis, and presentations through evidence links.
Do not rank students by commits, PR counts, or portfolio length.

Correct missing or inaccurate credit with a focused PR that links the evidence
and explains the correction. Ask affected collaborators to review shared-work
attribution. Keep grades and private student feedback outside this public record.
